## Contrato exato da api (Task 2, já implementada e aprovada — `api-tozzo.uk`,
## `modules/establishments/` + `modules/product-types/`) — NÃO precisa ler o repo
## da api, o contrato completo está aqui:

### Enum de categoria (fixo, 6 valores)

```
HAMBURGUERIA | PIZZARIA | SORVETERIA | CAFETERIA | LANCHONETE | OUTRO
```

### `GET /estabelecimentos`

Retorna o estabelecimento do usuário autenticado, incluindo `category` (uma das 6
strings, ou `null`). Sem parâmetro de rota. Qualquer role autenticado pode ler.

### `PATCH /establishments/:id`

**RBAC: `OWNER` ou `MANAGER`** (403 pra outra role). `:id` = `establishmentId` do
próprio usuário (senão 404). Body: `{ "category": "HAMBURGUERIA" }`. 400 se
ausente/inválida. 200 com o estabelecimento atualizado.

### `POST /tipos`

**RBAC: só `OWNER`** (403 pra `MANAGER`/outros — mais restrito que o PATCH acima).
Body: `{ "description": "Lanches", "color": "#9E9E9E" }` (aceita `descricao`/`cor`
também, use os nomes em inglês). 201 com o tipo criado. Sem endpoint de criação em
lote — chame uma vez por tipo confirmado.

## Rulings do controller (o plano não detalha estes pontos — decisão já tomada,
## siga como está, registre no relatório se discordar de algo)

1. **Este é um widget de configuração PERSISTENTE, não um onboarding de
   primeiro-acesso-só** (diferente da Task 9 mobile). Portanto:
   - O campo de categoria (`Select` das 6 opções + botão salvar, chamando só
     `PATCH /establishments/:id`) fica sempre visível/editável na página de
     configurações pra `OWNER` e `MANAGER` (mesmo RBAC do endpoint).
   - A lista de sugestão de tipos + botão de criar em lote (`POST /tipos` N
     vezes) é uma ação SEPARADA, visível/habilitada só pra `OWNER` (mesmo RBAC do
     endpoint) — não dispare automaticamente toda vez que a categoria for trocada,
     senão um `OWNER` que edita a categoria 3 vezes acaba criando tipos
     duplicados (não há dedupe/idempotência no `POST /tipos`, confirmado na Task
     9). Um botão explícito tipo "Adicionar tipos sugeridos" ao lado/abaixo do
     seletor de categoria, mostrando a lista sugerida pra categoria selecionada
     no momento, é a forma mais segura.
   - Pra `MANAGER`: mostre o seletor de categoria normalmente (ele pode salvar),
     mas esconda ou desabilite o botão/lista de sugestão de tipos (evita 403
     silencioso).
2. Use o `useAuth()` (`src/contexts/AuthContext.tsx`) já existente no projeto pra
   ler o `role` do usuário autenticado — o padrão já é usado em várias páginas do
   dashboard (`Navbar.tsx`, `EmployeesPage.tsx`, etc.), siga o mesmo estilo.
3. Chamadas à api: use a instância `api` já configurada em `src/services/api.ts`
   (axios com interceptors de auth/wire format já prontos) — `api.get('/estabelecimentos')`,
   `api.patch('/establishments/:id', {...})`, `api.post('/tipos', {...})`. Não
   crie um client fetch novo do zero.
4. Textos: siga o padrão i18n já usado em `SettingsPage.tsx`
   (`useTranslation('settings')`) — adicione as chaves novas no namespace
   `settings` existente, nos locales que o projeto já suporta.
